# Mechanic Specification

Цель — передать **принятые правила** в реализацию без необходимости додумывать ключевые решения.

## Подход

1. Определи **что уже решено**, что делает система сейчас, что нужно изменить, а что сохранить неизменным. Если доступен репозиторий/файлы, проверь реальное состояние перед указанием конкретных модулей или API. Если доступ отсутствует, не выдумывай пути, функции, имена стора и существующие классы.
2. Выбери границы и глубину по `../../references/framework.md`, достаточные для однозначного и проверяемого поведения. Для сложной системы раздели требования по механикам и их взаимодействиям. Опиши сценарии: Input или иной Trigger → условия → решение → изменение состояния/данных → обратная связь. Используй пять блоков как внутреннюю проверку полноты, а не обязательные разделы ответа.
3. Проверь **контракт механики** по `../../references/framework.md`: предусловия, входные данные и инициирующие события, результат, инварианты, взаимодействия. Зафиксируй правила переходов, приоритеты и ограничения. Если применимо, определи владение сущностями, сохранение, конкурентные операции, оффлайн/возврат, отмену и восстановление после ошибки. Контракт не требует отдельного раздела в каждом ТЗ.
4. Укажи что меняется в UI: статус, индикаторы, причины disabled и сообщения об ошибках. Избегай необоснованных дополнительных окон.
5. Отдельно выдели **не менять**: текущий баланс, цены, публичные контракты, сохранения, приоритеты или что-то ещё — согласно контексту. Не вводи новые игровые решения под видом технической детали.
6. Дополни контракт конкретными **критериями приёмки** в виде проверяемых условий (given / when / then или короткие сценарии): контракт проверяет полноту правил, сценарии — их выполнение. Укажи критические крайние случаи, но не раздувай список до очевидных формальностей.
7. Если есть неоднозначность, меняющая игровое правило, отметь её как вопрос/допущение; не выдавай гипотезу за согласованный факт. Для некритичных деталей выбери разумный вариант и обозначь его.

## Глубина ответа

- По словам «короткое ТЗ», «только суть» — обычно 1 цель, 3–7 требований, 2–5 проверок, без большой лекции о классификации.
- Для сложной новой системы уместны модель состояний, данные/сохранение, взаимодействия, UX, таблица случаев.
- Не создавай отдельную «механику» из каждой технической операции и не навязывай архитектуру кода без данных о текущем проекте.
- Не пиши код, если пользователь попросил только ТЗ. Не включай вымышленные требования по аналитике и монетизации.

## Границы режима

ТЗ — не пространство для незаметного расширения feature scope. Идеи по развитию можно вынести в необязательное примечание, но не в список обязательных требований.

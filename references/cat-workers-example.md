# Пример: автоматические работники в игре про расчёсывание котов

**Назначение:** иллюстрировать метод, а не задавать канонические правила для любой версии проекта. При работе с настоящим репозиторием сначала проверь его фактическую реализацию.

## Выбор глубины

По [общей методике](framework.md) один пример можно рассматривать на разных уровнях:

- **Система:** автоматизация работников — найм/улучшения, доступные редкости, назначение котов, выполнение работы и награда связаны через работников, очередь и экономику.
- **Механика:** назначение кота работнику — подбор подходящего незарезервированного кота для свободного работника и согласованное изменение занятости.
- **Правило:** проверка квалификации и доступной редкости — разрешённая галочка не заменяет проверку квалификации; оба ограничения участвуют в допустимости назначения.

Для обсуждения роли автоматизации достаточно состава системы и связей из дизайнерского уровня ниже. Для вопроса «почему работник не берёт кота?» полезно детализировать назначение и проверку допустимости; для алгоритма выбора первого подходящего кота — ещё и порядок обхода очереди и случай отсутствия кандидатов. Конкретные приоритеты и неустановленные правила нужно проверить в проекте или согласовать, а не придумывать.

Не нужно дробить проверку редкости на чтение каждого поля и другие очевидные технические операции, если это не устраняет неоднозначность.

## Дизайнерский уровень

- **Цель:** перевести часть ручного игрового цикла в автоматизацию и дать игроку задачи по управлению салоном.
- **Решения:** нанять нового работника или улучшить существующего; какие редкости ему доступны; как организовать поток заказов.
- **Цикл:** кот появляется в очереди → сотрудник берёт подходящего кота → выполняет работу → генерирует награду → освобождается → проверяет очередь снова.

На этом уровне достаточно связей: найм/улучшения и настройки задают доступность работы; назначение связывает очередь с занятостью работника; завершение работы связывает прогресс, награду и следующий подбор. Длительность и формула награды относятся к своим механикам и не нужны для узкого разбора выбора кота.

На границе системы команды найма, прокачки и изменения разрешённых редкостей — Input. Ниже граница уже: рассматривается только назначение кота.

## Пять блоков для выбранной механики: назначение кота

**Trigger:** появление подходящего кота или завершение предыдущей работы могут вызвать новый подбор. Это события, а не отдельный Input. При изменении настроек нужно проверить, когда проект повторяет подбор; пример не устанавливает это правило.

| Блок | Пример |
| --- | --- |
| Input | У автономного подбора отдельный Input может отсутствовать; команда от управляющей подсистемы была бы Input, только если такая команда есть в проекте |
| Detection | Свободен ли работник; есть ли в очереди подходящий незарезервированный кот; доступна ли редкость по квалификации |
| State & Logic | `idle` / `working` / `waiting`; выбор по принятому приоритету очереди с учётом квалификации и разрешённых редкостей; переход при назначении или отсутствии цели |
| Transformation | Резервирование выбранного кота, изменение занятости работника и состояния карточки |
| Communication | Очередь сообщает о кандидатах; назначение согласует резервирование и занятость работника; UI получает статус |

**Feedback:** под карточкой объяснить состояние («Работает», «Ждёт кота», «Нет подходящих котов»), а не заставлять угадывать, почему сотрудник не действует.

## Вопросы для ТЗ, если они не определены

- Если одновременно освободились два работника, кто резервирует первого кота? Должна быть единая процедура назначения без двойного резервирования.
- Что произойдёт при запрете редкости во время работы? Продолжить текущий заказ или отменить его — **неизвестно до выбора правила**.
- Что произойдёт при перезапуске страницы? Как сохраняются резервирование и оставшееся время?
- Как рассчитывается оффлайн-прогресс, и допускается ли генерация новых котов во время отсутствия?

**Важно:** пример не предписывает архитектуру классов, store или событийной шины. Это следующий этап, зависящий от текущего кода.
